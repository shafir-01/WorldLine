# AGENTS.md: guidance for GitLab Duo agents and flows working in WORLDLINE

This file follows the AGENTS.md convention read by GitLab Duo Chat, custom agents and flows (https://docs.gitlab.com/user/duo_agent_platform/customize/agents_md/). Keep it short and literal. `.gitlab/duo/chat-rules.md` holds style rules; this file holds project facts and the repair contract.

## What WORLDLINE is

WORLDLINE answers: what would a system do if the world were different, and which differences matter? It runs a deterministic simulated world from `scenarios/*.yaml`, branches it with fault interventions (delay, drop, duplicate, reorder, corrupt, revoke, clock_skew), checks three-valued invariants (PASS / FAIL / UNKNOWN) with witnesses, minimises a failing fault schedule to a 1-minimal counterexample (ddmin), abstracts it into a portable FailureGenome, and records typed evidence in a signed, hash-chained bundle. A kernel (`worldline verify`, `worldline authorize`) decides whether a release is AUTHORIZED or DENIED. Agents produce traces, patches and candidate evidence; the kernel decides. Read `docs/ARCHITECTURE.md` before changing any module signature.

| `worldline/cli/` | Typer app `worldline` | Yes |
| `scenarios/` | Scenario YAML; regression scenarios live here | Yes (this is where repairs usually land) |
| `tests/` | pytest + hypothesis | Yes, add tests; never delete or skip a failing test |
| `ui/` | Vite + React + TS static viewer | Yes |
| `experiments/out/` | Generated by CI; never hand-edit | No |
| **`invariants/`** | Invariant declarations (`*.yaml`), the specification of correctness | **No** |

| **`worldline/evidence/`** | Evidence records, Bundle, Policy, authorize: the kernel | **No** |

Off-limits paths are enforced by `CODEOWNERS` (owner `@shafir-01`) plus protected-branch code-owner approval. An MR touching them will not be mergeable from an agent session. If a task seems to require changing them, stop and say so in the MR description instead.

## Toolchain and commands

- Python 3.12, `uv`. Install: `pip install uv && uv sync --extra dev`.
- Tests: `uv run pytest -q`. A single file: `uv run pytest -q tests/test_core.py`.
- CLI (under construction; check `uv run worldline --help` for current flags):
  - `uv run worldline run scenarios/port_alert.yaml --seed 42`
  - `uv run worldline explore scenarios/port_alert.yaml --budget 200 --seed 42 --out experiments/out`
  - `uv run worldline minimize experiments/out/exploration.json --out experiments/out`
  - `uv run worldline genome extract ... | challenge ...`
  - `uv run worldline verify` and `uv run worldline authorize` are kernel commands; run them read-only, never change their inputs under `policies/`.
- UI: `cd ui && npm ci && npm run build` (Node 20).
- Determinism check: run the same command twice; `Trace.digest` must be byte-identical. If it is not, that is the bug.

## Reading a FAIL witness

A `VerdictRecord` has `invariant_id`, `result`, `witness` (list of event ids), `explanation`, `missing_data`, `trace_digest`. For `result == FAIL`, `witness` is the minimal set of event ids that form the counterexample. Look them up in `Trace.truth` (what happened) and in `Trace.views[role]` (what that role had received, with `received_time_ns`). For the `decision` invariant the witness is the truth events that were missing from the actor's view at `at_ns`: the decision was wrong because of what the actor did not yet know. For `UNKNOWN`, `missing_data` names the signal that was absent; that is not a bug in the invariant, it is a scenario without enough instrumentation.

## Reading a genome

`FailureGenome.mechanism` is a list of abstract interventions (selectors by `kind`, `role`, `nth`, relative timing; never concrete event ids). `preconditions` lists structural features a scenario must have for the mechanism to apply. `origin` points at the scenario, seed, branch and trace digest it came from. `evidence_kind` is `EMPIRICALLY_VALIDATED` on the origin only. A `ChallengeResult` says whether the genome `reproduced` on a second scenario; `preconditions_met == false` means the genome does not apply, which is a legitimate outcome, not a failure to report as a bug. Transfer is within the shared Event v1 substrate across scenarios; never describe it as transfer across codebases.

## The repair contract

A repair MR is acceptable only if all of the following hold:

1. The branch that produced the FAIL (same scenario, same seed, same minimal fault schedule) now yields PASS for the target invariant, shown by re-running `explore`/`run` with the same inputs and quoting the new digest in the MR description.
2. No invariant was weakened: `invariants/` and `worldline/evidence/` are untouched, and no check in `worldline/invariants/` became more permissive (no widened windows, no removed conditions, no `UNKNOWN` where there used to be `FAIL`).
3. A regression scenario was added under `scenarios/regressions/<invariant>_<short>.yaml` that instantiates the minimal fault schedule concretely, plus a test in `tests/` asserting PASS on it.
4. `uv run pytest -q` passes; no test was deleted, skipped or marked xfail.
5. The MR description states: the invariant id and version, the witness event ids before the fix, the mechanism in one sentence, what changed and why, and the claim ceiling (`EMPIRICALLY_VALIDATED`, never `ATTESTED`; only the kernel emits ATTESTED).
6. No wall-clock time, no randomness outside `DeterministicRNG`, no LLM call in the simulated world's decision path.
7. The repair is not vacuous: alongside the PASS on the minimal fault schedule, include a scenario variant (or test) in which the repaired rule still produces its non-default option when the evidence supports it. A rule that can no longer reach `escalate` has not been repaired, it has been disabled. State reachability explicitly in the MR description.

Fixes that only change the scenario so the fault no longer occurs are not repairs; they are deletions of the test case. A repair changes a decision rule, a delivery policy, an actor's required signals, or runner code so the system tolerates the fault.

## Non-negotiables

- Never fabricate numbers. `experiments/out/benchmark.json` is written by code that ran.
- Every FAIL has a witness list of event ids. Every UNKNOWN names the missing signal.
- Every public claim carries its `EvidenceKind` and its claim ceiling.
- Prefer small, reviewable MRs. One invariant per repair MR.
